# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a [CONTAINERlab](https://containerlab.dev/) network lab of [FRRouting (FRR)](https://frrouting.org/) nodes demonstrating Segment Routing MPLS (SR-MPLS) — IS-IS Prefix-SIDs over an IPv4 underlay as the transport for BGP L3VPN services (IPv4 forwards end-to-end; the IPv6 control plane works but cannot install — parked, see below) and global-table BGP, plus a live PCEP session to an external PCE (`pola`) as the foundation for SR-TE policy control. It is a config/infra repo, not an application: the "source code" is FRR configuration files, container init shell scripts, and a CONTAINERlab topology definition. See `images/topology.png` for a visual representation of the lab topology. `README.md`'s Network Resources tables are the authoritative current state.

This is an independent lab, not a variant of or dependent on any other repo.

## Lab lifecycle commands

There is no build/lint/test suite here — "testing" a change means redeploying the lab and inspecting control-plane/data-plane state via `vtysh`.

- `make lab` (or `sudo modprobe mpls_router mpls_iptunnel mpls_gso && sudo clab deploy -t lab.yml`) — load host MPLS kernel modules, then deploy the topology; applies each node's `frr.conf` and runs its init script
- `make clean` (or `clab destroy -t lab.yml`) — tear down the lab
- `make inspect` — show running lab state
- `make <node>` — drop into `vtysh` on an FRR router (`p1`–`p6`, `pe11`, `pe12`, `rr14`, `bdr13`), or a shell for `c1`/`c2`/`c3`/`pola`
- Direct access: `docker exec -it clab-frr-sr-mpls-<node> vtysh` or `bash`
- Packet capture on the host: `sudo ip netns exec clab-frr-sr-mpls-<node> tcpdump -nni <iface>`

Containers here share the host kernel's MPLS dataplane, so `sudo modprobe mpls_router mpls_iptunnel mpls_gso` **must** run on the host before `clab deploy` — `make lab` does this automatically.

## Repository structure

Each FRR router has its own directory (`pe11/`, `pe12/`, `p1/`–`p6/`, `rr14/`, `bdr13/`) containing a consistent 4-file set, all bind-mounted into the container by `lab.yml`:

- `frr.conf` — the FRR configuration (interfaces, IS-IS + segment-routing, BGP, VRF, and — on `pe11` only — `pathd` PCEP/PCC config)
- `daemons` — which FRR daemons run (`isisd` everywhere; `bgpd` on `pe11`/`pe12`/`rr14`/`bdr13` only; `pathd` on `pe11` only, as the SR-TE/PCEP headend)
- `vtysh.conf` — empty on every node
- `<node>.sh` — container init script run at deploy time (log-dir setup, `ip route del default`, per-core-interface `net.mpls.conf.<iface>.input=1` + `net.mpls.platform_labels`, and on PEs, VLAN subinterfaces + Linux VRF devices for RED/BLUE). `rr14.sh` is the exception — no MPLS sysctl setup at all, since `rr14` has no SR/MPLS dataplane role. The PEs additionally set `net.ipv6.conf.all.forwarding=1` for their client-facing IPv6 subinterfaces.

To change a router's behavior, edit its `frr.conf` and/or `.sh`, then redeploy. `lab.yml` is the single source of truth for topology — node roles, management IPs, and the interface link map; `frr.conf` interface `description` lines mirror these links, so cross-reference `lab.yml` when tracing what a given `ethN` connects to.

Other directories:

- `clients/` — `client1.sh`/`client2.sh`/`client3.sh` for the `wbitt/network-multitool` client containers (c1→pe11, c2→pe12, c3→pe11 on a separate interface), adding VLAN subinterfaces into the RED/BLUE VRFs (c1/c2 only — c3 is a plain global-table client, no VLAN/VRF).
- `pola/` — the external PCE: `polad.yaml` (server config, TED disabled), `sr-policies/` (YAML inputs for the `pola sr-policy add` CLI), `pola-logs/` (bind-mounted log dir). `pola/sr-policies/pe1-RED-pce-via-p3.yaml` references the pre-rename `pe1` node/loopback — being tackled separately alongside rebuilding the SR-TE policy demo, not currently a working example.
- `logs/` — per-node FRR logs, gitignored except `.gitkeep`.
- `clab-frr-sr-mpls/` — gitignored, generated by CONTAINERlab at deploy time (runtime state, TLS certs, inventories); not source

Not present in this lab (by design): `grafana/`, `loki/`, `promtail/` (no monitoring stack).

## Network design conventions

- Loopbacks double as router IDs: `172.16.0.y/32` per node.
- Core (underlay) links: IPv4 `/31`s (RFC 3021), packed sequentially within the single `10.0.1.0/24` block (see README for the full table). Six core routers (`p1`–`p6`) form a ring plus one diagonal chord (`p2`–`p5`); the `p2`–`p5` and `p5`–`p6` links both carry an explicit `isis metric 100` bump on both ends, biasing SPF away from that side of the ring — this is the intended hook for a future SR-TE "the SPF-preferred path is somewhere else" demo (not currently built — see below).
- **Both PEs are dual-homed into the core**: `pe11`→`p1`+`p4`, `pe12`→`p6`+`p3`, giving two fully disjoint 4-hop paths between the PEs. They are **not** equal-cost: `pe11-p1-p2-p3-pe12` costs 40 (all default metric 10), while `pe11-p4-p5-p6-pe12` costs 130 because it traverses the metric-100 `p5–p6` link. Plain SPF therefore always picks the `p1-p2-p3` path and never load-balances. The expensive path existing at all is the point — it's the path only a constraint (Flex-Algo affinity / SR-TE) can select.
- **Link affinities** (`affinity-map RED bit-position 0` / `affinity-map BLUE bit-position 1`, defined identically on every SR node; interfaces colored via zebra's `link-params` → `affinity <NAME>` → `exit-link-params` on both ends). **Do not use `isis affinity flex-algo NAME`** — it's in FRR's current online docs but does not exist in 10.7.1, and `vtysh -b` drops it silently with no error (verified against the live 10.7.1 CLI: the `interface` node has no affinity command; only `link-params` does). RED colors the cheap path (`pe11-p1-p2-p3-pe12`), BLUE colors the expensive one (`pe11-p4-p5-p6-pe12`). Cross-links (`p1↔p4`, `p2↔p5`, `p3↔p6`) and the `rr14`/`bdr13` attachments are deliberately left uncolored so a constrained Flex-Algo can't hop between planes mid-path. Bit positions stay ≤31 for Standard Administrative-Group compatibility. No Flex-Algo Definition consumes these yet — the coloring is the groundwork.
- IS-IS: single Level-2 area, NET `49.0001.1721.6000.00yy.00` where `yy` is the loopback's last octet zero-padded to 4 digits (e.g. `pe11` = `.11` → `0011`).
- Segment Routing: SRGB `16000–23999` is FRR's **default** — `segment-routing global-block` is deliberately not configured anywhere, so label = `16000 + index`. Algo-0 Prefix-SID index is `100 + last loopback octet` (e.g., `pe11` = 111 → 16111, `p5` = 106 → 16106). `rr14` has no `segment-routing on` at all — it's a route-reflector-only leaf with no MPLS dataplane role.
- **Flex-Algo is NOT configured — deliberately removed, do not re-add without checking upstream first.** [FRR #20022](https://github.com/FRRouting/frr/issues/20022) (open, unfixed, no root cause): Flex-Algo doesn't work in an `is-type level-2-only` domain. Config is accepted, but the FAD is never advertised or elected and per-algo node SIDs are never distributed — `show isis flex-algo` shows `Source: Not found` on every node. Reproduced here on 10.7.1; upstream confirms 10.1.1/10.4.1. It works at level-1 per the reporter, but switching `is-type` was deliberately declined to keep a realistic L2 backbone. It was configured, proven broken, then removed entirely. The intended design (algo 128 = RED / 129 = BLUE, `affinity include-any`, per-algo Prefix-SID index `200+octet` / `300+octet`, and the VRF steering: color 128/129 SR-TE policies + `route-map vpn import`, `pe12` needs `pathd`) is recorded in README's Flex-Algo section for if/when the bug is fixed.
- **`mpls-te on` is retained on all 8 SR nodes with colored links even though Flex-Algo is gone** — it's what makes isisd flood the admin-group/ASLA sub-TLVs, so removing it would leave the link colouring present in config but invisible in the LSDB. Keep it. (`bdr13`/`rr14` don't have it: no colored links.)
- **BGP-LS/TED is built, proven working, and parked — do not debug it as a config problem.** `pe11` exports the full LSDB via `mpls-te export` → zebra → `address-family link-state link-state` → `gobgp` (172.28.1.21), and 50 NLRIs arrive correctly with node names, router IDs, SRGB and metrics. But **FRR 10.7.1's BGP-LS encoder omits the Prefix-SID** — every PREFIXv4 NLRI arrives with `"prefix":{}`. pola gets the SRGB base but never the per-prefix index, so it cannot build a label stack. Dynamic path computation is impossible on this FRR version. Admin-groups and adjacency-SIDs are likewise not encoded (so affinity-constrained PCE computation is also out), and the link metric is corrupted in transit (`isis metric 100` → `igp_metric: 36`). `pola/polad.yaml` has `ted.enable: false` with the reason inline.
- **`mpls-te export` exports the full LSDB; `distribute link-state` exports local-only** (tried on `rr14`: produced only its own node + prefix, 2 NLRIs vs 50). They're mutually exclusive, as is every `mpls-te` command with `distribute link-state`. Consequence: the core does **not** need `bgpd` on P routers — one exporter covers the whole topology. Also, `distribute link-state` requires a clean daemon start; adding it to a running bgpd leaves it unregistered with no retry.
- Both routes to using pola are currently blocked: dynamic paths need the TED (no Prefix-SIDs), and explicit paths need `pola sr-policy add -s`, which is broken in v1.3.3 (`addSRPolicyWithoutSIDValidation()` sets neither `Asn` nor `SidValidate`). Using pola requires an FRR fix or a one-line pola patch.
- Dynamic MPLS label pool: `mpls label dynamic-block 700000 799999` (zebra), used by `label vpn export auto` (VPN labels) — kept disjoint from the SRGB and the static `pathd` binding-SID range (`30000–30099`).
- BGP: ASN 65000, PEs (`pe11`, `pe12`) and the border router (`bdr13`) peer with route reflector `rr14` over IPv4 (loopback `update-source`) — a single IPv4 transport carrying `ipv4 unicast`, `ipv4 vpn` and `ipv6 vpn`. L3VPN uses `label vpn export auto` inside **each** `address-family ipv4 unicast` / `ipv6 unicast` block under `router bgp ... vrf X` — it does **not** sit at the vrf-instance level; FRR silently no-ops it there. RED and BLUE each get **two** independently-allocated dynamic labels (one per AF), not one. RED VRF = RT `65000:10`, BLUE VRF = RT `65000:20`.
- **BGP Labeled-Unicast (RFC 3107) is not used anywhere in this lab** — confirmed absent from every node's config. The global-table demo (`pe11`↔`bdr13`, `10.11.1.0/30`/`99.99.99.99/32`) runs over plain `address-family ipv4 unicast`, relying on BGP next-hop resolution recursing through the IS-IS SR LSP to the next-hop's loopback — no per-prefix label is needed since `99.99.99.99/32` is directly connected on `bdr13` itself, not a further destination behind it. See README's "Global Table" section.
- **IPv6-in-VRF (6VPE) is PARKED — control plane works, dataplane is blocked by the Linux kernel. Do not debug it as a config problem.** The RED/BLUE IPv6 config on the client-PE side is deliberately retained and correct; `ping6 c1 → c2` fails and is expected to. vpnv6 export/reflect/import all work and are provable via `show bgp ipv6 vpn` / `show bgp vrf RED ipv6 unicast`. The route never reaches `show ipv6 route vrf RED`.
  - Root cause: **Linux cannot install an IPv6 route with an IPv4 next-hop.** `net/ipv6/route.c` rejects `RTA_VIA` unconditionally — `ip -6 route add ... encap mpls 16112/700003 via inet 10.0.1.1 dev eth1` returns `Error: IPv6 does not support RTA_VIA attribute`. 6VPE/6PE *require* an IPv4-mapped next-hop (that's what keeps the core IPv4-only), so the one form the RFCs mandate is the one form Linux cannot install. FRR's side is correct. Symptom when the next-hop is resolvable: `B>r` (rejected) plus `Route install failed` / `RTM_NEWROUTE ... Invalid argument` in the log.
  - The same route with `via inet6 fe80::...` is accepted and **forwards correctly over the unmodified IPv4-only core** (verified by hand). So it's the mixed address family, not MPLS-on-IPv6, and not the label stack. The upstream fix is small: zebra already resolves `::ffff:172.16.0.12` to `via 10.0.1.1 dev eth1` and would need to emit that adjacency's IPv6 link-local instead. Report not yet filed.
- **Dual-stacking the IS-IS core was built, verified working, and deliberately reverted — do not re-add it.** IPv6 IS-IS + IPv6 loopbacks + IPv6 Prefix-SIDs (index `400+octet`) makes `ping6` work with a proper two-label stack and TI-LFA. It was reverted because it doesn't fix 6VPE, it removes the need for it: the value of 6PE/6VPE is IPv6 service over a core that never learns an IPv6 route, and once the P routers carry IPv6 Prefix-SIDs this lab has drifted into the separate SRv6 lab's premise. A working `ping6` is not worth the premise. **The core is IPv4-only, by design.**
- **`pe11`/`pe12`/`rr14` each carry an unrouted `ipv6 address 2001:db8::y/128` on `lo`** — not in IS-IS, no Prefix-SID, purely a session-enablement placeholder. All three activate `address-family ipv6 vpn`, and FRR 10.7.1 with **zero** local IPv6 addresses anywhere doesn't just skip that AF — it fails OPEN processing and CEASEs the whole session (`%NOTIFICATION: sent ... 6/0 (Cease/Unspecific)`, logged as `EC 33554453: No local IPv6 address, and zebra does not support V6 routing with v4 nexthops`), which was originally misdiagnosed as a capability mismatch since the received OPEN is well-formed. `bdr13` never activates `ipv6 vpn` and doesn't need one.
- **No `::ffff:` address exists anywhere in this lab, deliberately — do not reintroduce one.** Earlier revisions used `::ffff:172.16.0.y/128` on the theory it would double as a resolvable vpnv6 next-hop. It doesn't (see the kernel limitation above), and on the route reflector it causes a real bug: `rr14` holding `::ffff:172.16.0.14/128` **substitutes its own address** into reflected vpnv6 routes. Its RIB and `advertised-routes` both read `::ffff:172.16.0.12` while `tshark` showed `::ffff:172.16.0.14` on the wire; `neighbor RR attribute-unchanged next-hop` did not help. An RR must not rewrite the next-hop at all.
- **Verify vpnv6 next-hop behaviour on a fresh `make lab`, never on a live edit.** FRR selects the local vpnv6 next-hop **at session establishment and caches it**. Changing `lo` addresses or applying an outbound `set ipv6 next-hop global` route-map on a running `bgpd` does not recompute it, and `clear bgp ipv6 vpn * soft out` re-sends the attribute without recomputing the cached local value. Several conclusions in this investigation were artifacts of exactly that and only a full redeploy revealed the real behaviour. Same class of trap as `distribute link-state` needing a clean daemon start.
- **`net.ipv6.conf.all.forwarding=1` is set in `pe11.sh`/`pe12.sh` only** — it defaults to `0` in a container netns and neither FRR nor containerlab enables it (IPv4's is on by default, which is why only IPv6 was affected). The PEs are the only nodes with IPv6 interfaces; the IPv4-only core has no IPv6 to forward.
- **TI-LFA**: every ISIS interface on every SR-capable node (`pe11`, `pe12`, `p1`–`p6`, `bdr13`) runs `isis fast-reroute ti-lfa level-2 node-protection link-fallback` — precomputed sub-second local repair on link/node failure, no dependency on full SPF reconvergence. `rr14` is excluded (no `segment-routing on`, no SR dataplane role). Verified working, including node protection and adjacency-SID-based strict repair paths.
- **Testing TI-LFA needs SPF deliberately stalled on the PLR** — default reconvergence is tens of milliseconds and carries zero packets, so a ping-loss test proves nothing (plain SPF reconvergence looks identical). `tc`/netem delay does not help (adds packet latency, not convergence latency), and `netem loss 100%` is worse than useless (interface stays UP, no link-down event, TI-LFA never fires, blackholes for the full hold time). Apply `spf-delay-ietf init-delay 30000 ...` temporarily on the PLR, capture the multi-label repair stack on the backup egress, then remove it. It is deliberately **not** in any `frr.conf` — lab instrument, not lab config. Procedure in VALIDATION.md Layer 4.

## SR-TE / PCE state (as of the 2026-09-24 topology sync)

`pe11` runs `pathd` and has a configured PCEP session to `pola` (`pce-initiated`, `pcc peer POLA`) — this is real and live-testable via `show sr-te pcep session` / `show sr-te pcep pcc`. **However, `pe11/frr.conf` currently has no `segment-list` or `policy` blocks at all** — the static explicit-path SR-TE demo that used to exist on the pre-rename `pe1` node (two colored policies toward `pe2`, a `STEER-RED-VIA-P3` route-map) was removed as part of this topology change and has not been rebuilt for the new 6-core-router topology. `pola/sr-policies/pe1-RED-pce-via-p3.yaml` is a stale, pre-rename artifact (references the deleted `pe1` node and its old loopback) — don't treat it as a working example without regenerating it against `pe11`'s current identity first.

If/when rebuilding this: `pola`'s own TED is disabled (`ted.enable: false`), so any policy pushed through it needs either explicit segment-lists (raw MPLS labels or `nai`-based segments, see prior session's pathd research) or TED enabled first.
