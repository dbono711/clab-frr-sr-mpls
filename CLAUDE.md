# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a [CONTAINERlab](https://containerlab.dev/) network lab of [FRRouting (FRR)](https://frrouting.org/) nodes demonstrating Segment Routing MPLS (SR-MPLS) — IS-IS Prefix-SIDs over an IPv4 underlay as the transport for IPv4/IPv6 BGP L3VPN services, plus BGP Labeled-Unicast for global-table transport and native `pathd` SR-TE policies. It is a config/infra repo, not an application: the "source code" is FRR configuration files, container init shell scripts, and a CONTAINERlab topology definition. See `images/topology.png` for a visual representation of the lab topology.

## Lab lifecycle commands

There is no build/lint/test suite here — "testing" a change means redeploying the lab and inspecting control-plane/data-plane state via `vtysh`.

- `make lab` (or `sudo modprobe mpls_router mpls_iptunnel mpls_gso && sudo clab deploy -t lab.yml`) — load host MPLS kernel modules, then deploy the topology; applies each node's `frr.conf` and runs its init script
- `make clean` (or `clab destroy -t lab.yml`) — tear down the lab
- `make inspect` — show running lab state
- `make pe1` / `pe2` / `p1` / `p2` / `p3` / `p4` / `rr` / `bdr1` — drop into `vtysh` on that router
- `make c1` / `c2` / `c3` — shell into a client container
- Direct access: `docker exec -it clab-frr-sr-mpls-<node> vtysh` or `bash`
- Packet capture on the host: `sudo ip netns exec clab-frr-sr-mpls-<node> tcpdump -nni <iface>`

Containers here share the host kernel's MPLS dataplane, so `sudo modprobe mpls_router mpls_iptunnel mpls_gso` **must** run on the host before `clab deploy` — `make lab` does this automatically.

## Repository structure

Each router has its own directory (`pe1/`, `pe2/`, `p1/`–`p4/`, `rr/`, `bdr1/`) containing a consistent 4-file set, all bind-mounted into the container by `lab.yml`:

- `frr.conf` — the FRR configuration (interfaces, IS-IS + segment-routing, BGP, VRF, and — on `pe1` only — `pathd` SR-TE policy)
- `daemons` — which FRR daemons run (`isisd` everywhere; `bgpd` on `pe1`/`pe2`/`rr`/`bdr1` only; `pathd` on `pe1` only, as the SR-TE headend)
- `vtysh.conf` — empty on every node
- `<node>.sh` — container init script run at deploy time (log-dir setup, `ip route del default`, per-core-interface `net.mpls.conf.<iface>.input=1` + `net.mpls.platform_labels`, and on PEs, VLAN subinterfaces + Linux VRF devices for RED/BLUE)

To change a router's behavior, edit its `frr.conf` and/or `.sh`, then redeploy. `lab.yml` is the single source of truth for topology — node roles, management IPs, and the interface link map (`p1:eth2` ↔ `p2:eth1`, etc.); `frr.conf` interface `description` lines mirror these links, so cross-reference `lab.yml` when tracing what a given `ethN` connects to.

Other directories:

- `clients/` — `client1.sh`/`client2.sh`/`client3.sh` for the `wbitt/network-multitool` client containers (c1→pe1, c2→pe2, c3→pe1), adding VLAN subinterfaces into the RED/BLUE VRFs.
- `logs/` — per-node FRR logs, gitignored except `.gitkeep`
- `clab-frr-sr-mpls/` — gitignored, generated by CONTAINERlab at deploy time (runtime state, TLS certs, inventories); not source

Not present in this lab (by design, this pass): `grafana/`, `loki/`, `promtail/` (no monitoring stack), `scripts/` (no external controller — the SR-TE steering demo is native `pathd` config, not a script), `ROUTE-EXPORT-VALIDATION.md`.

## Network design conventions

- Loopbacks double as router IDs: `172.16.0.y/32` per node.
- Core (underlay) links: IPv4 `/31`s (RFC 3021), all packed sequentially within the single `10.0.1.0/24` block (see README for the full table); `p3`–`p4` carries an explicit `isis metric 100` bump on both ends, used later as the SR-TE lab's "the SPF-preferred path is somewhere else" leg.
- IS-IS: single Level-2 area, NET `49.0001.xxxx.xxxx.xxxx.00` derived from the router ID (zero-pad each RID octet to 3 digits, concatenate, regroup as 4+4+4, wrap in `49.0001.`/`.00`).
- Segment Routing: SRGB `16000–23999` (`segment-routing global-block`), identical on every SR node; each node's Prefix-SID index/label is `region + node number` (e.g., `pe1` = index 101 / label 16101). `rr` has no `segment-routing on` at all — it's a route-reflector-only leaf with no MPLS dataplane role.
- Dynamic MPLS label pool: `mpls label dynamic-block 700000 799999` (zebra), used by `label vpn export auto` (VPN labels) and BGP Labeled-Unicast — kept disjoint from the SRGB and the static `pathd` binding-SID range (`30000–30099`).
- BGP: ASN 65000, PEs (`pe1`, `pe2`, `bdr1`) peer with route reflector `rr` over IPv4 (loopback `update-source`). L3VPN uses `label vpn export auto` inside **each** `address-family ipv4 unicast` / `ipv6 unicast` block under `router bgp ... vrf X` (confirmed against FRR's own feature-announcement config notation: `label vpn export` nests under `address-family <afi> unicast`, same level as `rd vpn export` — it does **not** sit at the vrf-instance level). RED and BLUE each get **two** independently-allocated dynamic labels (one per AF), not one. Putting `label vpn export auto` at the vrf-instance level is a silent no-op: `vtysh -b` rejects it at that context and moves on, so it never shows up in `show running-config`, and the VRF quietly exports routes with `implicit-null` instead. RED VRF = RT `65000:10`, BLUE VRF = RT `65000:20`.
- A BGP peer cannot be activated for both `ipv4 unicast` and `ipv4 labeled-unicast` on the same session (FRR enforces `BGP_ERR_PEER_SAFI_CONFLICT`) — where both are logically needed (`rr`), `ipv4 labeled-unicast` replaces `ipv4 unicast` entirely. A `network` statement under `ipv4 unicast` still works without activating a neighbor there; the labeled-unicast SAFI draws from that RIB.
- **`pe1`/`pe2`/`rr` each need a local IPv6 address** (`ipv6 address ::ffff:172.16.0.y/128` on `lo`, unrouted/not in ISIS) purely because all three activate `address-family ipv6 vpn`. Confirmed live: without any local IPv6 address anywhere, FRR 10.7.1 doesn't just skip negotiating that AF — it fails OPEN processing entirely and CEASEs the whole session (`%NOTIFICATION: sent ... 6/0 (Cease/Unspecific)`, logged as `EC 33554453: No local IPv6 address, and zebra does not support V6 routing with v4 nexthops`), which was misdiagnosed at first as a capability mismatch since the received OPEN itself is perfectly well-formed. `bdr1` never activates `ipv6 vpn` and doesn't need this — confirmed its `ipv4 labeled-unicast` session to `rr` establishes fine without it.
- **The `lo` IPv6 address must be IPv4-mapped, not an arbitrary native address.** It's not just a session-establishment placeholder — it's the real vpnv6 `next-hop-self` value advertised to peers for RED/BLUE's IPv6 side. FRR's own 6VPE behavior specifically expects an IPv4-mapped next-hop (`::ffff:a.b.c.d`) so it resolves recursively via the IPv4 RIB instead.

The global/default-table scaffold between `pe1` and `bdr1` (`10.11.1.0/30` / `99.99.99.99/32`) uses BGP Labeled-Unicast (RFC 3107) here instead of a locally-generated service SID, and it **works end-to-end** — no VRF/Linux-VRF-device dependency exists in the BGP-LU forwarding path. See "Global Table: BGP Labeled-Unicast" in README.md.

**Open risk, not yet validated live**: `pe1`'s `pathd` SR-TE demo (two colored policies to `pe2`, `route-map ... set sr-te color`) attaches the route-map to the RED VRF's `ipv4 unicast` AF via `route-map vpn import`. This specific BGP-color-into-pathd-policy combination is less commonly exercised than plain SR-TE policy config and was authored from FRR documentation, not confirmed against a live deploy as of this writing. Both `pathd` policies/segment-lists are real and independently verifiable via `show sr-te policy` (confirmed against FRR source, `pathd/path_cli.c` — the earlier documented guess of `show segment-routing traffic-eng policy` was wrong and doesn't exist as a command) regardless of whether the route-map steering resolves as expected — see README.md's "Manual SR-MPLS Traffic Steering" section for the documented fallback. Both policies (color 100/binding-sid 30000, color 200/binding-sid 30001) already show up correctly in `show mpls table` with their resolved label stacks, confirming the `pathd` config itself works independent of the BGP-color-steering question.
