# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a [CONTAINERlab](https://containerlab.dev/) network lab of [FRRouting (FRR)](https://frrouting.org/) nodes demonstrating Segment Routing MPLS (SR-MPLS) — IS-IS Prefix-SIDs over an IPv4 underlay as the transport for IPv4/IPv6 BGP L3VPN services and global-table BGP, plus a live PCEP session to an external PCE (`pola`) as the foundation for SR-TE policy control. It is a config/infra repo, not an application: the "source code" is FRR configuration files, container init shell scripts, and a CONTAINERlab topology definition. See `images/topology.png` for a visual representation of the lab topology — **note the image predates the current topology and needs regenerating**; `README.md`'s Network Resources tables are the authoritative current state.

This is an independent lab, not a variant of or dependent on any other repo (e.g. a sibling SRv6 lab) — do not reference or assume shared context with anything outside this directory.

## Lab lifecycle commands

There is no build/lint/test suite here — "testing" a change means redeploying the lab and inspecting control-plane/data-plane state via `vtysh`.

- `make lab` (or `sudo modprobe mpls_router mpls_iptunnel mpls_gso && sudo clab deploy -t lab.yml`) — load host MPLS kernel modules, then deploy the topology; applies each node's `frr.conf` and runs its init script
- `make clean` (or `clab destroy -t lab.yml`) — tear down the lab
- `make inspect` — show running lab state
- `make <node>` — drop into `vtysh` on an FRR router (`p1`–`p6`, `pe11`, `pe12`, `rr14`, `bdr13`), or a shell for `c1`/`c2`/`c3`/`pola`
- Direct access: `docker exec -it clab-frr-sr-mpls-<node> vtysh` or `bash`
- Packet capture on the host: `sudo ip netns exec clab-frr-sr-mpls-<node> tcpdump -nni <iface>`

Containers here share the host kernel's MPLS dataplane, so `sudo modprobe mpls_router mpls_iptunnel mpls_gso` **must** run on the host before `clab deploy` — `make lab` does this automatically.

## Repository structure

Each FRR router has its own directory (`pe11/`, `pe12/`, `p1/`–`p6/`, `rr14/`, `bdr13/`) containing a consistent 4-file set, all bind-mounted into the container by `lab.yml`:

- `frr.conf` — the FRR configuration (interfaces, IS-IS + segment-routing, BGP, VRF, and — on `pe11` only — `pathd` PCEP/PCC config)
- `daemons` — which FRR daemons run (`isisd` everywhere; `bgpd` on `pe11`/`pe12`/`rr14`/`bdr13` only; `pathd` on `pe11` only, as the SR-TE/PCEP headend)
- `vtysh.conf` — empty on every node
- `<node>.sh` — container init script run at deploy time (log-dir setup, `ip route del default`, per-core-interface `net.mpls.conf.<iface>.input=1` + `net.mpls.platform_labels`, and on PEs, VLAN subinterfaces + Linux VRF devices for RED/BLUE). `rr14.sh` is the exception — no MPLS sysctl setup at all, since `rr14` has no SR/MPLS dataplane role.

To change a router's behavior, edit its `frr.conf` and/or `.sh`, then redeploy. `lab.yml` is the single source of truth for topology — node roles, management IPs, and the interface link map; `frr.conf` interface `description` lines mirror these links, so cross-reference `lab.yml` when tracing what a given `ethN` connects to.

Other directories:

- `clients/` — `client1.sh`/`client2.sh`/`client3.sh` for the `wbitt/network-multitool` client containers (c1→pe11, c2→pe12, c3→pe11 on a separate interface), adding VLAN subinterfaces into the RED/BLUE VRFs (c1/c2 only — c3 is a plain global-table client, no VLAN/VRF).
- `pola/` — the external PCE: `polad.yaml` (server config, TED disabled), `sr-policies/` (YAML inputs for the `pola sr-policy add` CLI), `pola-logs/` (bind-mounted log dir). `pola/sr-policies/pe1-RED-pce-via-p3.yaml` references the pre-rename `pe1` node/loopback — being tackled separately alongside rebuilding the SR-TE policy demo, not currently a working example.
- `logs/` — per-node FRR logs, gitignored except `.gitkeep`.
- `clab-frr-sr-mpls/` — gitignored, generated by CONTAINERlab at deploy time (runtime state, TLS certs, inventories); not source

Not present in this lab (by design): `grafana/`, `loki/`, `promtail/` (no monitoring stack).

## Network design conventions

- Loopbacks double as router IDs: `172.16.0.y/32` per node.
- Core (underlay) links: IPv4 `/31`s (RFC 3021), packed sequentially within the single `10.0.1.0/24` block (see README for the full table). Six core routers (`p1`–`p6`) form a ring plus one diagonal chord (`p2`–`p5`); the `p2`–`p5` and `p5`–`p6` links both carry an explicit `isis metric 100` bump on both ends, biasing SPF away from that side of the ring — this is the intended hook for a future SR-TE "the SPF-preferred path is somewhere else" demo (not currently built — see below).
- IS-IS: single Level-2 area, NET `49.0001.1721.6000.00yy.00` where `yy` is the loopback's last octet zero-padded to 4 digits (e.g. `pe11` = `.11` → `0011`).
- Segment Routing: SRGB `16000–23999` (`segment-routing global-block`), identical on every SR node; each node's Prefix-SID index/label is `100 + last loopback octet` (e.g., `pe11` = index 111 / label 16111, `p5` = index 106 / label 16106). `rr14` has no `segment-routing on` at all — it's a route-reflector-only leaf with no MPLS dataplane role.
- Dynamic MPLS label pool: `mpls label dynamic-block 700000 799999` (zebra), used by `label vpn export auto` (VPN labels) — kept disjoint from the SRGB and the static `pathd` binding-SID range (`30000–30099`).
- BGP: ASN 65000, PEs (`pe11`, `pe12`) and the border router (`bdr13`) peer with route reflector `rr14` over IPv4 (loopback `update-source`). L3VPN uses `label vpn export auto` inside **each** `address-family ipv4 unicast` / `ipv6 unicast` block under `router bgp ... vrf X` — it does **not** sit at the vrf-instance level; FRR silently no-ops it there. RED and BLUE each get **two** independently-allocated dynamic labels (one per AF), not one. RED VRF = RT `65000:10`, BLUE VRF = RT `65000:20`.
- **BGP Labeled-Unicast (RFC 3107) is not used anywhere in this lab** — confirmed absent from every node's config. The global-table demo (`pe11`↔`bdr13`, `10.11.1.0/30`/`99.99.99.99/32`) runs over plain `address-family ipv4 unicast`, relying on BGP next-hop resolution recursing through the IS-IS SR LSP to the next-hop's loopback — no per-prefix label is needed since `99.99.99.99/32` is directly connected on `bdr13` itself, not a further destination behind it. See README's "Global Table" section.
- **`pe11`/`pe12`/`rr14` each need a local IPv6 address** (`ipv6 address ::ffff:172.16.0.y/128` on `lo`, unrouted/not in ISIS) purely because all three activate `address-family ipv6 vpn`. Confirmed live: without any local IPv6 address anywhere, FRR 10.7.1 doesn't just skip negotiating that AF — it fails OPEN processing entirely and CEASEs the whole session (`%NOTIFICATION: sent ... 6/0 (Cease/Unspecific)`, logged as `EC 33554453: No local IPv6 address, and zebra does not support V6 routing with v4 nexthops`), which was misdiagnosed at first as a capability mismatch since the received OPEN itself is perfectly well-formed. `bdr13` never activates `ipv6 vpn` and doesn't need this.
- **The `lo` IPv6 address must be IPv4-mapped, not an arbitrary native address.** It's not just a session-establishment placeholder — it's the real vpnv6 `next-hop-self` value advertised to peers for RED/BLUE's IPv6 side. FRR's own 6VPE behavior specifically expects an IPv4-mapped next-hop (`::ffff:a.b.c.d`) so it resolves recursively via the IPv4 RIB instead.
- **TI-LFA**: every ISIS interface on every SR-capable node (`pe11`, `pe12`, `p1`–`p6`, `bdr13`) runs `isis fast-reroute ti-lfa level-2 node-protection link-fallback` — precomputed sub-second local repair on link/node failure, no dependency on full SPF reconvergence. `rr14` is excluded (no `segment-routing on`, no SR dataplane role). See VALIDATION.md Layer 4 for steady-state and failover verification commands.

## SR-TE / PCE state (as of the 2026-09-24 topology sync)

`pe11` runs `pathd` and has a configured PCEP session to `pola` (`pce-initiated`, `pcc peer POLA`) — this is real and live-testable via `show sr-te pcep session` / `show sr-te pcep pcc`. **However, `pe11/frr.conf` currently has no `segment-list` or `policy` blocks at all** — the static explicit-path SR-TE demo that used to exist on the pre-rename `pe1` node (two colored policies toward `pe2`, a `STEER-RED-VIA-P3` route-map) was removed as part of this topology change and has not been rebuilt for the new 6-core-router topology. `pola/sr-policies/pe1-RED-pce-via-p3.yaml` is a stale, pre-rename artifact (references the deleted `pe1` node and its old loopback) — don't treat it as a working example without regenerating it against `pe11`'s current identity first.

If/when rebuilding this: `pola`'s own TED is disabled (`ted.enable: false`), so any policy pushed through it needs either explicit segment-lists (raw MPLS labels or `nai`-based segments, see prior session's pathd research) or TED enabled first.
